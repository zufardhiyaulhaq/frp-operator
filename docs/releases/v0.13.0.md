Releasing v0.13.0 FRP Operator 🥳🥳

Helm chart 1.11.0.

This release lets the operator run **frps** itself. A new `Server` resource runs frps in a cluster that has a public IP, and private clusters connect their `Client`s and `ServerPool` servers to it. It also fixes how a `Client` mounts its TLS files and adds `tls.serverName`.

## New: `Server` (alpha)

> **Alpha.** `Server` is new in this release. Its API (`frp.zufardhiyaulhaq.com/v1alpha1`, kind `Server`) and behaviour may change in a later release without a migration path; try it before relying on it in production.

A `Server` becomes one frps pod (`fatedier/frps:v0.71.0`, the same frp release as frpc) behind a public Service (`LoadBalancer` by default, or `ClusterIP`), plus a separate Service for the dashboard and metrics when either is enabled.

- **Ports**: `bind.port` / `kcpPort` / `quicPort` for frpc, `vhost` HTTP/HTTPS/TCPMUX ports, and `allowPorts.tcp` / `allowPorts.udp` for TCP and UDP Upstreams. Only declared ports are exposed. With no `allowPorts`, TCP and UDP Upstreams are refused.
- **Tunnel TLS**: `bind.tls.certificate` (your Secret), `bind.tls.clientCA` for mTLS, and `bind.tls.force` (default `true`). Without a certificate, frps uses its own random one that clients cannot verify, and the Server gets a `TunnelTLSUnverified` warning.
- **Authentication**: a token from your Secret, or one the operator generates.
- **Dashboard and metrics**: frps's dashboard, admin API and Prometheus `/metrics` on port 7500, behind one login (generated if you don't provide one), with optional HTTPS. They are exposed only through their own Service, never an Ingress. An optional `ServiceMonitor` is available.
- **Restarts**: frps cannot reload its configuration, so any change restarts the frps pod, and connected Clients reconnect on their own. With `restartPolicy: Manual` the operator waits until you delete the pod. An evicted pod is replaced.
- **Status**:
  - `status.address` is the Client's `host`, read from the Service's `status.loadBalancer.ingress`.
  - `status.tls.serverNames` holds the names a Client can verify the certificate against.
  - `status.exposedPorts` lists the ports Upstreams can claim.
  - `status.connectionSecret` is the Secret you copy to private clusters: it holds `token`, and `ca.crt` when your certificate Secret has one.
  - Conditions `Ready` and `ConfigSynced`. An invalid spec shows `ConfigSynced=False/InvalidConfig`, and the running pod keeps serving.
- **Security**: frps runs as a non-root user with every Linux capability dropped. Ports below 1024 work through the safe sysctl `net.ipv4.ip_unprivileged_port_start=0`.
- **Static IP**: put your cloud's annotation in `service.annotations`. It is copied to the Service as-is. The Service is updated in place and never recreated, so its IP survives every change except deleting the Server.
- **Limits**: one frps pod per Server. The public Service holds at most `server.maxPorts` ports (chart value, default 50; operator flag `--server-max-ports`). A cloud that rejects mixed TCP/UDP load balancers shows `Ready=False/LoadBalancerFailed`. frps cannot read PROXY protocol.

See the README section "Server (frps)" and [`examples/server`](https://github.com/zufardhiyaulhaq/frp-operator/tree/v0.13.0/examples/server).

## New fields

- `Client.spec.server.tls.serverName` (and `ServerPool` `servers[].tls.serverName`): the name frpc verifies the server certificate against (`transport.tls.serverName`). It defaults to `host`, so it is needed when `host` is an IP and the certificate only names a DNS name.

## Fixes

- **Client TLS files are mounted from the references you set.** Before, the operator mounted one whole Secret at `/etc/frp/tls`. That had three effects:
  - with `certFile` and `trustedCaFile` in different Secrets, frpc read `ca.crt` from the certificate Secret;
  - a `trustedCaFile` ConfigMap was not mounted at all;
  - every `key` field was ignored.

  Each file now comes from its own Secret or ConfigMap and key.

## Behaviour changes

- **Every existing `Client` that uses TLS restarts once after the upgrade.** That is how it picks up the corrected mount. From now on, a Client pod is also recreated whenever its TLS settings change, because frpc reads TLS files and `serverName` only at start.
- **TLS `key` fields now matter.** A key that does not exist in its Secret or ConfigMap now shows as `ConfigSynced=False/InvalidConfig` with a Warning event. Before, it went unnoticed.

## How to Upgrade

The CRDs changed (new `Server` CRD, and `tls.serverName` on `Client` and `ServerPool`), and Helm never upgrades CRDs. Apply them first:
```
kubectl apply -f https://raw.githubusercontent.com/zufardhiyaulhaq/frp-operator/v0.13.0/charts/frp-operator/crds/crds.yaml
```
Then upgrade the chart:
```
helm repo update
helm upgrade frp-operator frp-operator/frp-operator --version 1.11.0
```
