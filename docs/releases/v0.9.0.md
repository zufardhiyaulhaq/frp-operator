Releasing v0.9.0 FRP Operator 🥳🥳

Helm chart 1.7.0.

Changes:
1. frpc upgraded from v0.65.0 to v0.71.0. This brings the UDP proxy-protocol fix (header sent only on the first packet of a session), binary WebSocket/WSS tunnel frames, and server-side security fixes — please upgrade frps as well. Use an frps at least as new as the one you ran before.
2. `enabled: false` on `Upstream` and `Visitor` to pause a tunnel without deleting the resource. A disabled resource releases its server/visitor port so another resource can take it; it stays in the frpc config with `enabled = false`.
3. `transport.wireProtocol` on `Client` (`v1` | `v2`). `v2` enables an AEAD-encrypted control channel and requires frps >= v0.69.0. Unset keeps frpc's default (`v1`).
4. `loadBalancer` (`group`, `groupKey`) on HTTP and HTTPS `Upstream`, matching TCP (HTTPS load-balancer groups require frps >= v0.66.0).
5. Every `Client` now sets `clientID` (default `"<namespace>/<name>"`, visible in the frps dashboard client list on frps >= v0.67.0). frps allows only one online client per clientID:
   - If you apply the same manifests against one frps from several clusters, set `spec.clientID: ""` to omit it, or give each cluster a distinct value. Apply the new CRDs first — older CRDs drop the `clientID` field.
   - A graceful pod restart reconnects immediately. After an unclean pod death (node loss, network partition) frps may keep the old session registered for up to ~90 s; until then the new pod's login is refused, frpc exits, and the container restarts with backoff until frps releases the session.
6. frpc v0.70.0+ rejects configs with duplicate proxy or visitor names. The operator now rejects duplicate names with a descriptive error before writing the config. Rename any `Upstream`/`Visitor` that shares a name with another one referencing the same `Client` (the operator matches on `spec.client` across namespaces).
7. The operator runs `frpc verify` inside the pod before every reload; a rejected config is reported on the Client's `ConfigSync` condition and is not hot-reloaded.
8. The operator recreates the frpc pod when its image differs from the desired one (previously pods were created once and never updated).

## How to Upgrade

Helm by default doesn't update the CRDs, you need to apply the CRDs manually:
```
kubectl apply -f https://raw.githubusercontent.com/zufardhiyaulhaq/frp-operator/v0.9.0/charts/frp-operator/crds/crds.yaml
```

After upgrading the operator, each existing client pod is rolled once to frpc v0.71.0 automatically (a few seconds of tunnel downtime per client). Old frpc pods cannot load the new config on a restart, so do not skip this step by pinning the old operator with new CRDs.

Example — pause an upstream and opt into wire protocol v2:
```yaml
apiVersion: frp.zufardhiyaulhaq.com/v1alpha1
kind: Upstream
spec:
  enabled: false
  ...
---
apiVersion: frp.zufardhiyaulhaq.com/v1alpha1
kind: Client
spec:
  server:
    transport:
      wireProtocol: v2
```
