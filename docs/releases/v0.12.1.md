Releasing v0.12.1 FRP Operator 🥳🥳

Helm chart 1.10.1.

This patch release makes an invalid `Client` configuration visible. v0.12.0 turned several silent misconfigurations (most notably a missing Secret or Secret key) into errors, but those errors only reached the operator log: the `Client` kept reporting `ConfigSynced=True` and `frp_client_config_synced` stayed at `1`.

## Fixes

- When the operator cannot build a Client's frpc config, the `Client` now gets:
  - condition `ConfigSynced=False` with reason `InvalidConfig` and the error as the message (`kubectl describe client <name>`),
  - a `Warning` event with reason `InvalidConfig`,
  - `frp_client_config_synced` set to `0`.

  The last good config keeps running and the reconcile is retried; once the spec is fixed the condition returns to `True`. Causes include a missing Secret or key, an invalid `transport.proxyURL` / `proxyCredentials`, a proxy combined with `kcp`/`quic`, a sub-second dial duration, a TCP upstream without `port` or `plugin`, and duplicate server/visitor ports.
- Client conditions keep their `lastTransitionTime` until their status actually changes. It used to be rewritten on every reconcile, causing a status write (and another reconcile) each time.

## Alerting

`frp_client_config_synced == 0` now covers invalid specs as well as failed reloads, for example:

```yaml
- alert: FrpClientConfigNotSynced
  expr: frp_client_config_synced == 0
  for: 5m
  annotations:
    summary: "frp Client {{ $labels.namespace }}/{{ $labels.client }} is not running its current config"
```

## How to Upgrade

No CRD changes since v0.12.0. Upgrade the chart:
```
helm repo update
helm upgrade frp-operator frp-operator/frp-operator --version 1.10.1
```

Coming from v0.11.0 or earlier, apply the CRDs first and read the v0.12.0 notes:
```
kubectl apply -f https://raw.githubusercontent.com/zufardhiyaulhaq/frp-operator/v0.12.1/charts/frp-operator/crds/crds.yaml
```

**Full Changelog**: https://github.com/zufardhiyaulhaq/frp-operator/compare/v0.12.0...v0.12.1
