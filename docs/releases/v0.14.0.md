Releasing v0.14.0 FRP Operator 🥳🥳

Helm chart 1.12.0.

This release adds a log level for frps and frpc, moves both to frp v0.71.1, and makes sure every new frpc pod starts on the current configuration.

## New fields

- **`log.level`** on `Client` (frpc), `Server` (frps) and a ServerPool's `clientTemplate` (frpc in every generated Client):
  ```yaml
  spec:
    log:
      level: debug   # trace | debug | info (default) | warn | error
  ```
  - frpc and frps always log to stdout. Every rendered `frpc.toml` and `frps.toml` now states `log.to = "console"` and `log.level`.
  - **Server:** a level change restarts frps. With `restartPolicy: Manual` it waits until you delete the pod, and shows `ConfigSynced=False/RestartPending` until then.
  - **Client:** a level change recreates the frpc pod, because frpc applies log settings only at start. Leaving the level unset or at `info` recreates nothing.
  - **ServerPool:** changing `clientTemplate.log.level` recreates every generated frpc pod of that pool at about the same time.
  - **Invalid levels:** the CRD accepts only these five levels. The operator also rejects anything else with `ConfigSynced=False/InvalidConfig` and a Warning event, for example when an old CRD lets a value through.

## Fixes

- **New frpc pods start on the current configuration.** Whenever the operator starts an frpc pod, it now writes the desired ConfigMap first. That covers a changed image, TLS settings or log level, an evicted pod and a pod deleted by hand. Before, a TLS change such as a new `tls.serverName` could recreate the pod on the old `frpc.toml`. The hot reload that followed did not apply it, so frpc kept the old setting.

## frp v0.71.1

frpc (`fatedier/frpc:v0.71.1`) and frps (`fatedier/frps:v0.71.1`) move from v0.71.0 to v0.71.1, a fixes-only frp release. Among the fixes: control connections no longer get stuck after a failed write, and work connections are now closed when server-side bandwidth limiting is enabled. Two of its fixes change behaviour:

- `healthCheck.maxFailed` now counts **consecutive** failures; the count resets after a success.
- An HTTP `CONNECT` tunnel request (TCPMUX) that carries a body (a positive content length or a transfer encoding) now gets HTTP 400.

## Behaviour changes on upgrade

- **Every frpc pod is recreated once**, because of the new frpc image. Each tunnel is down for a few seconds.
- **Every frps restarts once**, because of the new frps image and the `log.*` keys now written into `frps.toml`. Connected frpc clients reconnect on their own.
- **Servers with `restartPolicy: Manual`** show `ConfigSynced=False/RestartPending` after the upgrade, until you delete their frps pod.

## How to Upgrade

The CRDs changed (new `log` field on `Client`, `Server` and `ServerPool`), and Helm never upgrades CRDs. Apply them first:
```
kubectl apply -f https://raw.githubusercontent.com/zufardhiyaulhaq/frp-operator/v0.14.0/charts/frp-operator/crds/crds.yaml
```
Then upgrade the chart:
```
helm repo update
helm upgrade frp-operator frp-operator/frp-operator --version 1.12.0
```
