# frps Server CRD — design

Agreed with the owner in a brainstorming session on 2026-10-11 (Q1–Q10, design sections 1–4) and a
grilling session the same day (G1–G20). This is the source of truth for the implementation plan.

## Goal

Let frp-operator run **frps** in a Kubernetes cluster that has a public IP (typically through a
`LoadBalancer` Service). Private clusters running frp-operator then connect their Clients and
ServerPools to it. Today the operator only manages the client side and points at frps servers
that someone else runs.

## Decisions

### Brainstorming

| # | Decision |
|---|---|
| Q1 | A new **`Server`** custom resource, reconciled by the operator (not a static chart mode, not docs only) |
| Q2 | Public ports are **declared** on the Server (`allowPorts`) and expanded into the Service; nothing is exposed dynamically |
| Q3 | The Server publishes a **connection Secret** (`token`, `ca.crt`); you copy it to private clusters with any tool. No cross-cluster credentials |
| Q4 | **No new client-side connection field.** The connection Secret's keys match what Client and ServerPool already use (`authentication.token.secret`, `tls.trustedCaFile`); the address comes from `status.address` |
| Q5 | v1 scope: bind ports, allowPorts, vhost, token auth, tunnel TLS / mTLS, Service options, dashboard + metrics, `podTemplate`. Out: server-side OIDC, frps server plugins, multiple replicas |
| — | frps runs as **one bare Pod** (owner question). frps instances share no state, so more than one replica behind one load balancer breaks routing; availability comes from several Servers plus a private-side ServerPool |
| Q6 | `allowPorts` is **split by protocol** (`tcp`, `udp`), so the Service carries no unneeded UDP and doesn't double the load-balancer listeners |
| Q7 | API fields are **grouped by who connects**: `bind` (frpc → frps), `allowPorts` and `vhost` (Internet → proxies) |
| Q8 | Tunnel TLS lives under **`bind.tls`**. vhost HTTPS is SNI passthrough; frps holds no website certificates |
| Q9 | The dashboard is exposed **only through a Service**, never an Ingress, and never on the proxy load balancer |
| Q10 | The dashboard can have its **own TLS certificate**. An exposed dashboard without one gets a Warning event |

### Grilling

| # | Decision |
|---|---|
| G1 | `service.type` is `LoadBalancer` or `ClusterIP`. `NodePort` is rejected (it remaps ports, so a `remotePort` could never be reached). `loadBalancerClass: frp.zufardhiyaulhaq.com/frp` is rejected (the operator's own ServerPool controller would claim it) |
| G2 | One proxy Service carries TCP and UDP. A cloud that rejects mixed protocols shows as `Ready=False/LoadBalancerFailed`; no split-Service option |
| G3 | frps gets `allowPorts` as the union of `tcp` and `udp` (frps has no per-protocol list). Documented: a UDP proxy on a TCP-only number is accepted by frps but unreachable; check `status.exposedPorts` |
| G4 | `spec.restartPolicy`: `Automatic` (default) restarts frps on any config change; `Manual` leaves the running config untouched and sets `ConfigSynced=False/RestartPending` until you delete the pod |
| G5 | Static IP only through `service.annotations` (no deprecated `loadBalancerIP`). The Service is patched in place, never recreated, so the IP survives |
| G6 | No `loadBalancerSourceRanges` on the proxy Service |
| G7 | No raw-TOML escape hatch. Typed fields only |
| G8 | The frps container runs as non-root with `NET_BIND_SERVICE` by default; `podTemplate.securityContext` overrides the pod-level part |
| G9 | Deleting `<server>-connection` rotates a generated token; the operator emits a Warning event `TokenRotated` |
| G10 | `metrics.serviceMonitor` without the ServiceMonitor CRD: skip it, Warning event `ServiceMonitorUnavailable`, the Server stays Ready |
| G11 | One PR (plan → native execution → code review), then release v0.13.0 |
| G12 | The Client gets **`tls.serverName`** (frpc `transport.tls.serverName`). ServerPool servers share the type, so they get it too. A certificate then needs a DNS name, not the load-balancer IP |
| G13 | Without `bind.tls`, frps uses its own random self-signed certificate. Nothing is generated by the operator |
| G14 | `bind.tls.force`, default `true` (frps `transport.tls.force`). Turn it off only for `wss` behind an external TLS terminator |
| G15 | mTLS client certificates are yours to issue (for example cert-manager in each private cluster) |
| G16 | No ports declared → frps gets the empty range `allowPorts = [{ start = 2, end = 1 }]`, so TCP/UDP proxies are refused |
| G17 | The server names to put in a Client's `tls.serverName` are published in `status.tls.serverNames` |
| G18 | Fix the Client's TLS mount in this PR: `certFile`, `keyFile` and `trustedCaFile` each come from their own Secret/ConfigMap and key |
| G19 | `status.tls.serverNames` = the DNS SANs read from your certificate. A certificate that doesn't parse or doesn't match its key is `InvalidConfig` |
| G20 | `bind.tls` omitted → Warning event `TunnelTLSUnverified` |

## Verified frp v0.71.0 facts this design relies on

- frps can't reload its configuration (frpc can), so any config change means restarting frps.
- frps `allowPorts` doesn't distinguish protocols: one list feeds a TCP and a UDP port manager
  (`server/service.go:175-176`). A TCP and a UDP proxy can claim the same number.
- Empty `allowPorts` allows every port (`server/ports/ports.go:63-77`). `allowPorts` is never
  validated, so `[{ start = 2, end = 1 }]` passes strict parsing and allows nothing.
- vhost HTTPS routes by TLS SNI and passes the encrypted stream through. TLS ends at the backend.
- If `vhostHTTPSPort == bindPort`, frpc's TLS handshakes go to the HTTPS vhost muxer first.
- The dashboard UI, its admin API (which includes `DELETE /api/proxies`) and `/metrics` share one
  web server behind one basic-auth login (`server/api_router.go:31-36`). `/healthz` is unauthenticated.
  `enablePrometheus` is silently ignored unless `webServer.port` is set. Dashboard TLS keys:
  `webServer.tls.certFile` / `keyFile`.
- `frps verify -c <file>` exists and is strict about unknown keys, like `frpc verify`.
- frpc checks the server certificate against `transport.tls.serverName`, or `serverAddr` when unset
  (`client/connector.go:192-195`). An IP `serverAddr` therefore needs an IP SAN.
- frpc with TLS on and no `trustedCaFile` skips verification (`pkg/transport/tls.go:150-152`); it does
  not fall back to the system roots.
- frps without `certFile`/`keyFile` generates a random self-signed certificate on every start, with no
  SANs (`pkg/transport/tls.go:99-105`).
- frps `transport.tls.force` rejects non-TLS connections on bind, kcp and websocket; quic is always TLS.
  Setting `transport.tls.trustedCaFile` forces TLS and requires a client certificate
  (`RequireAndVerifyClientCert`), including over quic.
- After a successful first login, frpc retries forever when frps goes away (backoff up to 20 s);
  `loginFailExit` only applies to the first login.
- frps does not read PROXY protocol on the bind port. Don't enable it on the load balancer.

## API

```yaml
apiVersion: frp.zufardhiyaulhaq.com/v1alpha1
kind: Server
metadata: {name: public-01, namespace: frp-system}
spec:
  bind:                                    # frpc → frps (the tunnel)
    port: 7000                             # required; tcp and websocket clients
    kcpPort: 7000                          # optional, UDP (kcp clients)
    quicPort: 7001                         # optional, UDP (quic clients)
    tls:                                   # optional; secures frpc ↔ frps only
      certificate: {secret: {name: frps-cert}}       # tls.crt, tls.key (+ ca.crt)
      clientCA: {secret: {name: frps-client-ca}}    # ca.crt → client certificates required (mTLS)
      force: true                          # default; false only for wss behind a TLS terminator
  allowPorts:                              # Internet → TCP/UDP Upstreams, one port per proxy
    tcp: ["8000-8010"]
    udp: ["5353"]
  vhost:                                   # Internet → HTTP/HTTPS/TCPMUX, shared by domain (optional)
    httpPort: 80
    httpsPort: 443
    tcpmuxPort: 5002
    subdomainHost: example.com
  authentication:
    token: {secret: {name: my-token, key: token}}   # optional; generated if omitted
  restartPolicy: Automatic                 # default; or Manual
  service:                                 # the public proxy Service
    type: LoadBalancer                     # default; or ClusterIP
    annotations: {}                        # static IPs, cloud LB options
    loadBalancerClass: ""
    externalTrafficPolicy: Cluster
  dashboard:
    enabled: false                         # UI + admin API on 7500
    credentials: {secret: {name: my-dashboard}}     # username/password; generated if omitted
    tls: {certificate: {secret: {name: frps-dashboard-cert}}}   # optional; HTTPS dashboard
    service:                               # dedicated Service, separate from the proxy Service
      type: ClusterIP                      # default; or NodePort / LoadBalancer
      annotations: {}
      loadBalancerClass: ""
      loadBalancerSourceRanges: []
  metrics:
    enabled: false                         # enablePrometheus; also starts the web server
    serviceMonitor: false
  podTemplate: {}                          # same shape as Client
status:
  address: 203.0.113.10                    # LB ingress IP/hostname, or <server>-frps.<ns>.svc for ClusterIP
  exposedPorts: {tcp: [...], udp: [...]}   # copy into a private ServerPool's allowedPorts
  connectionSecret: public-01-connection
  tls: {serverNames: [frps.example.com]}   # DNS SANs of bind.tls.certificate
  conditions: [Ready, ConfigSynced]
```

What each port group is for:

| Group | Who connects | Notes |
|---|---|---|
| `bind.port` / `kcpPort` / `quicPort` | frpc from private clusters | Chosen by the Client's `spec.server.protocol` (`tcp`/`websocket` → `port`, `kcp` → `kcpPort`, `quic` → `quicPort`). `wss` needs a TLS terminator in front of `port` and `bind.tls.force: false` |
| `allowPorts.tcp` / `.udp` | Internet users of TCP/UDP Upstreams | One port per proxy; frps opens it when a client claims it |
| `vhost.*` | Internet users of HTTP/HTTPS/TCPMUX Upstreams | One port shared by any number of domains, routed by Host / SNI / CONNECT host |

**Validation.** A failure sets `ConfigSynced=False/InvalidConfig` with a Warning event, and the previous pod keeps serving. The rules:
- every port is in 1–65535
- `bind`, `vhost` and `allowPorts` don't overlap within the same protocol (this also rejects `vhost.httpsPort == bind.port`)
- `kcpPort` ≠ `quicPort`
- the expanded public Service ports stay at or below the operator flag `--server-max-ports` (default 50)
- `service.type` is `LoadBalancer` or `ClusterIP`; `service.loadBalancerClass` is not `frp.zufardhiyaulhaq.com/frp`
- every referenced Secret and key exists
- `bind.tls.certificate` parses and matches its key

## Reconciliation

A new `ServerReconciler` owns these objects for each Server:

| Object | Name | Notes |
|---|---|---|
| Secret | `<server>-frps-config` | The rendered `frps.toml`. A Secret, because it holds the token |
| Secret | `<server>-connection` | `token` (generated once if `authentication` is omitted, otherwise copied from your Secret) + `ca.crt` (when `bind.tls.certificate` has one). This is what private clusters copy |
| Secret | `<server>-dashboard` | Generated `username`/`password`, only if `dashboard.credentials` is omitted and the web server runs |
| Pod | `<server>-frps` | Image `fatedier/frps:v0.71.0` (the same pin as frpc). Readiness = TCP on `bind.port`. Container: `runAsNonRoot`, `capabilities.add: [NET_BIND_SERVICE]`, `drop: [ALL]`, `allowPrivilegeEscalation: false`. `podTemplate` merged in |
| Service | `<server>-frps` | `spec.service.type` (default `LoadBalancer`). Bind ports, vhost ports and expanded `allowPorts`, each with its own protocol. Patched in place, never recreated |
| Service | `<server>-frps-web` | Dashboard, admin API and `/metrics` on 7500. Created only when `dashboard.enabled` or `metrics.enabled`. `dashboard.service.type` (default `ClusterIP`) |
| ServiceMonitor | `<server>-frps` | Only with `metrics.serviceMonitor`. Basic auth from the dashboard credentials; HTTPS when dashboard TLS is set. Skipped with a Warning event when the CRD is missing |

**Applying changes.** The pod carries an annotation holding a hash of the rendered config plus the content of every referenced Secret and the image. When the desired hash differs:
- `restartPolicy: Automatic` — write the config Secret, delete the pod, create a new one. The same flow Client uses for an image change.
- `restartPolicy: Manual` — leave `<server>-frps-config` untouched (a mounted Secret update would otherwise reach the pod on its next container restart), set `ConfigSynced=False/RestartPending`, emit an event. When the pod is gone (deleted by you, evicted, rescheduled), write the config and create the pod.

The reconciler **watches the Secrets a Server references**, so a rotated token or certificate takes effect at once (Automatic). Connected frpc clients reconnect on their own.

**Status:**

| Condition | Meaning |
|---|---|
| `Ready=True` | The pod is ready **and** `status.address` is set |
| `Ready=False/AddressPending` | The load balancer is still provisioning |
| `Ready=False/LoadBalancerFailed` | The cloud rejected the Service (for example mixed TCP/UDP); the cloud controller's `SyncLoadBalancerFailed` message is copied |
| `Ready=False/PodFailed` | The frps pod is crashing |
| `ConfigSynced=True` | The running pod has the current config hash |
| `ConfigSynced=False/InvalidConfig` | The spec is invalid; the previous pod keeps serving |
| `ConfigSynced=False/RestartPending` | `restartPolicy: Manual` and the running pod has an older config |

`status.address` is `Service.status.loadBalancer.ingress[0].ip` (or `.hostname`) for `LoadBalancer`, and `<server>-frps.<ns>.svc` for `ClusterIP`.

**Warning events:**

| Reason | When |
|---|---|
| `InvalidConfig` | Validation failed |
| `TunnelTLSUnverified` | `bind.tls` is unset: frps uses a random certificate that clients can't verify |
| `DashboardInsecure` | `dashboard.service.type` is `NodePort` or `LoadBalancer` and `dashboard.tls` is unset |
| `TokenRotated` | A generated token was regenerated because `<server>-connection` was deleted |
| `ServiceMonitorUnavailable` | `metrics.serviceMonitor` is set but the ServiceMonitor CRD is missing |

**Deletion.** Owner references remove every object. The load balancer's IP goes with it.

## Client changes (shared with ServerPool servers)

- **`spec.server.tls.serverName`** (string, optional) → frpc `transport.tls.serverName`. ServerPool server `tls` uses the same type and is passed through to the generated Client.
- **TLS mount fix.** Today the Client mounts one whole Secret at `/etc/frp/tls`: with `certFile` and `trustedCaFile` both set, `ca.crt` is read from the certificate Secret, a `trustedCaFile` ConfigMap is not mounted, and every `key` field is ignored. With mTLS and cert-manager that makes frpc trust the client CA instead of the server's. The fix mounts a projected volume at `/etc/frp/tls` that maps each reference's `{name, key}` to `tls.crt`, `tls.key` and `ca.crt` (Secret or ConfigMap source).

## Connecting a private cluster

1. **Public cluster:** apply the Server and wait for `status.address` and `Ready=True`.
2. **Copy `<server>-connection`** to the private cluster. A documented `kubectl get secret … | jq | kubectl apply` works, or any secret-sync tool.
3. **Private cluster:** write a normal Client (or a ServerPool server):
   - `host` = `status.address`, `port` = `bind.port`
   - `authentication.token.secret` → the copied Secret's `token`
   - `tls.trustedCaFile` → its `ca.crt`, and `tls.serverName` → one of `status.tls.serverNames` (when `bind.tls` is set)
   - mTLS: `tls.certFile` / `keyFile` → a client certificate you issued from the `clientCA`

   A ServerPool's `allowedPorts` should match `status.exposedPorts`; the docs say so.
4. **DNS for vhost:** point `customDomains`, or `*.<subdomainHost>`, at `status.address`.

## Testing

- **Unit:**
  - rendering `frps.toml` (every field, optional keys omitted when unset, strings quoted, the empty `allowPorts` range)
  - port expansion and validation (overlap, protocol split, max ports, service type and class)
  - certificate parsing (DNS SANs, key mismatch, garbage)
  - the config hash, Automatic and Manual restart paths
  - reading the address from the Service
  - the Client's `tls.serverName` render and the projected TLS volume
- **Real binary:** every Server feature rendered and checked with `frps verify` from the pinned image, extending `make test-frpc-config`.
- **e2e:**
  - A Server with `service.type: ClusterIP` (the e2e cluster has no cloud load balancer), and a Client connected to `<server>-frps.<ns>.svc` that carries TCP echo traffic.
  - A Server with your own certificate; the Client uses `trustedCaFile` + `serverName`.
  - mTLS where the Client's certificate and trusted CA live in different Secrets.
  - A spec change rolls the pod, and the Client reconnects.
  - A missing token key surfaces as `InvalidConfig`.
  - The dashboard Service answers with basic auth.

## Delivery

- **CRD:** a new `Server` CRD in `charts/frp-operator/crds/crds.yaml`; Client and ServerPool CRDs gain `tls.serverName`.
- **Chart:** RBAC for `servers`, and read access to `servicemonitors` / CRDs for the existence check.
- **Operator flag:** `--server-max-ports`.
- **Docs:** `examples/server/` with `server.yaml`, `client.yaml`, `upstream.yaml` and a README; a README section with per-cloud static-IP annotations and the limits above.
- **Release:** v0.13.0 (minor: new CRD). Release notes call out the Client TLS mount fix.
- **Jekyll:** the spec and plan are wrapped in raw tags, because GitHub Pages runs every Markdown file through Liquid.

## Out of scope

- server-side OIDC
- frps server plugins
- multiple frps replicas behind one load balancer
- any Ingress
- a client-side connection field
- cross-cluster automation (reading the Server from a private cluster)
- dynamic port exposure
- operator-generated tunnel certificates or client certificates
- a raw-TOML escape hatch
- PROXY protocol from the load balancer
